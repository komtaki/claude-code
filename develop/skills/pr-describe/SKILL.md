## 1. 呼び出しタイミング

資料を作る目的は、読み手が自分でコードを追わなくても妥当性を判断できる状態にすることにある。次の 2 つの入口がある。

### 1.1 自分の実装を説明する

複雑な実装を終えたら、PR を作る前に本スキルで資料を作る。`develop:pr-create` の手順 5 から呼ばれる。

次のいずれかに当てはまるものを複雑な実装とみなす。

- 複数のリポジトリにまたがる
- 読み手がコードを追わないと妥当性を判断できない
- 既存の挙動に依存した判断を含み、その依存がコードを見ないと分からない

当てはまらない実装では使わない。1 リポジトリ内で差分を読めば判断できる変更に資料を付けても、保守する対象が増えるだけになる。

### 1.2 他人の PR を説明する

レビュー依頼や共有のために、既存の PR の仕組みをまとめる場合も本スキルを使う。この場合は 2 章の読み方から始める。

## 2. 対象 PR を読む

### 2.1 clone してチェックアウトする

差分だけを読んで説明を書かない。呼び出し元・呼び出し先・型定義を追えないため、因果を取り違える。

```sh
gh repo clone 組織/リポジトリ repos/対象ディレクトリ
cd repos/対象ディレクトリ && gh pr checkout {番号}
```

`mise.toml` があるリポジトリは、続けて `mise trust` する。これを飛ばすと、リポジトリが固定したバージョンではなくグローバルの古いツールで動かすことになる。

### 2.2 リポジトリが固定したバージョンで検証する

手元の処理系で動かした結果を、そのまま PR の評価にしない。言語バージョンによって、同じコードが構文エラーにも正しいコードにもなる。

実例として、Python 3.14 の PEP 758 は括弧なしの `except A, B:` を認める。3.13 以前の `ast.parse` に通すと構文エラーになるが、これは PR の欠陥ではない。

検証は次の順で行う。

1. `.python-version` や `mise.toml` など、リポジトリが固定しているバージョンを読む
2. そのバージョンでテスト・型チェック・lint を実際に流す
3. 結果を資料に書くときは、コマンドと件数を添える

CI の pass だけを根拠にしない。新規ディレクトリが CI の対象に入っていないことがある。

### 2.3 未 resolve のレビューを確認する

`gh pr checks` が pass でも、bot のレビューは指摘を残したまま check を通す。未 resolve のスレッドは GraphQL で別途取得する。既出の指摘を資料に書き直さないため、また対応済みのまま resolve 漏れになっているものを見つけるために確認する。

## 3. コードの説明の粒度

資料の価値は、読み手が差分を読んでも分からない部分をどれだけ埋めたかで決まる。

### 3.1 「何をするか」ではなく「なぜその書き方か」を書く

関数名を言い換えただけの説明は、差分を読めば分かるので書かない。書くのは、その実装を選んだ理由と、他の書き方を選ばなかった理由になる。

- step を 2 つに分けた理由（片方の再試行で、成功済みの側を二重に作らないため）
- 例外を投げずにデータで返す理由（投げると後続の後始末に到達しないため）
- 値を関数の外ではなく中で取る理由（外で取ると再実行時にずれるため）

### 3.2 識別子と値は実物を書く

「数回リトライする」ではなく、定数名と値を書く。読み手がコードを grep できる語を本文に置く。

- 定数は `POLL_MAX_ATTEMPTS`（290）のように、名前と値を併記する
- 設定は環境変数名で書く
- エラーコード・ステータス値は、コード中のリテラルをそのまま書く

### 3.3 受け渡す型を示す

処理が複数の段に分かれる実装では、各段の戻り値の型を示す。型が分かると、段と段の間で何が保たれるかが読み取れる。

### 3.4 分岐は条件式を引用する

「条件によっては遅延する」と書かない。`shared_running >= 閾値` のように、判定式そのものを書く。読み手が境界値を検討できるようにするため。

### 3.5 書かないもの

- 追加した節名・ファイル名の列挙（差分で分かる）
- コードブロックの丸写し（必要なのは引用ではなくリンク）
- 未検証の推測（確認していないことは、確認していないと書く）

## 4. リンクの作り方

### 4.1 クリックできるリンクにする

`file:line` をそのまま書かない。GitHub のリンクにする。読み手が開いて確かめられること自体が、この資料の価値になる。

```
https://github.com/{owner}/{repo}/blob/{sha}/{path}#L{開始行}-L{終了行}
```

### 4.2 コミットの SHA に固定する

ブランチ名を指すリンクは、後のコミットで行がずれて別の箇所を指す。`main` や `HEAD` を使わない。

SHA は `git -C {リポジトリ} rev-parse HEAD` で取る。資料の末尾に、固定したコミットを明記する。読み手が「いつ時点のコードか」を判断できるようにするため。

### 4.3 リポジトリ名を添える

複数のリポジトリにまたがる資料では、パスだけではどのリポジトリか判別できない。各リンクにリポジトリ名を併記する。

## 5. 資料の組み立て

### 5.1 全体像の図を先に置く

処理の流れを扱う資料では、構成図を先に示してから各段の詳細に入る。読み手が現在地を見失わないようにするため。

図は次を満たす。インライン SVG の書き方は `artifact-diagramming` に従う。

- **矢印にラベルを付ける**: ラベルのない矢印は「何か関係がある」としか言えない。`polls every 300s` のように、何が流れるかを書く
- **境界を描く**: 別のクラウド・別のアカウント・別のリポジトリをまたぐ箇所は、ゾーンで囲って色を変える。どこで信頼境界を越えるかが、たいてい説明の中心になる
- **両テーマで読めるようにする**: 色はページのトークンから取る

### 5.2 出典は主張と同じ行に置く

出典を末尾にまとめると、読み手が主張と行き来することになる。処理の流れを説明する資料では、各ステップに「誰が誰に何を」と出典をセットで置く。

本文から出典を分離するかどうかの判断は `develop:docs-write` の 2.5 にある。本スキルは、分離したあとの資料をどう作るかを扱う。

### 5.3 設計の肝を独立させる

実装全体がひとつの制約から導かれている場合、その制約を独立した節にする。各段の説明に溶かし込むと、読み手が制約を再構成することになる。

## 6. 公開前の確認

### 6.1 共有範囲を確認する

アーティファクトは作成時の共有範囲が一定ではない。リンクを渡すときに、相手が開けるかどうかを伝える。開けない場合は共有操作が必要なことも添える。

### 6.2 リンクが機能することを確認する

SHA・パス・行番号のいずれかを取り違えると、リンクは開けるが別の箇所を指す。行番号は資料を書いた時点のものか確認する。
