## 1. 呼び出しタイミング

複雑な実装を終えたら、PR を作る前に本スキルで資料を作る。実装の妥当性を読み手が判断できる状態にするため。

次のいずれかに当てはまるものを複雑な実装とみなす。

- 複数のリポジトリにまたがる
- 読み手がコードを追わないと妥当性を判断できない
- 既存の挙動に依存した判断を含み、その依存がコードを見ないと分からない

当てはまらない実装では使わない。1リポジトリ内で差分を読めば判断できる変更に資料を付けても、保守する対象が増えるだけになる。

## 2. 適用範囲

読み手がコードと突き合わせて確認する資料を作るときに使う。アーティファクト、PR 本文、設計文書の付録が対象。

本文から出典を分離するかどうかの判断は `develop:docs-write` の 2.5 にある。本スキルは、分離したあとの資料をどう作るかを扱う。

## 3. リンクの作り方

### 3.1 クリックできるリンクにする

`file:line` をそのまま書かない。GitHub のリンクにする。読み手が開いて確かめられること自体が、この資料の価値になる。

形式は次の通り。

```
https://github.com/{owner}/{repo}/blob/{sha}/{path}#L{開始行}-L{終了行}
```

### 3.2 コミットの SHA に固定する

ブランチ名を指すリンクは、後のコミットで行がずれて別の箇所を指す。`main` や `HEAD` を使わない。

SHA は `git -C {リポジトリ} rev-parse HEAD` で取る。資料の末尾に、固定したコミットを明記する。読み手が「いつ時点のコードか」を判断できるようにするため。

### 3.3 リポジトリ名を添える

複数のリポジトリにまたがる資料では、パスだけではどのリポジトリか判別できない。各リンクにリポジトリ名を併記する。

## 4. 中身の書き方

### 4.1 出典は主張と同じ行に置く

出典を末尾にまとめると、読み手が主張と行き来することになる。処理の流れを説明する資料では、各ステップに「誰が誰に何を」と出典をセットで置く。

### 4.2 図を添える

処理の流れを扱う資料では、全体像を図で示してから各ステップの詳細に入る。読み手が現在地を見失わないようにするため。

### 4.3 差分で分かることを書かない

PR 本文では、追加した節名やファイル名の列挙をしない。差分を見れば分かる。本文に書くのは、差分からは読み取れない経緯と判断。

## 5. 公開前の確認

### 5.1 共有範囲を確認する

アーティファクトは作成時の共有範囲が一定ではない。リンクを渡すときに、相手が開けるかどうかを伝える。開けない場合は共有操作が必要なことも添える。

### 5.2 リンクが機能することを確認する

SHA・パス・行番号のいずれかを取り違えると、リンクは開けるが別の箇所を指す。行番号は資料を書いた時点のものか確認する。
