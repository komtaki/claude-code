## 0. 執筆前の準備（最優先）

書き始める前に、対象ドキュメントが依存する一次情報を必ず読む。

* **参照リンクを辿る**: 本文に「〜に従う」「参照」「@mention」「リンク先」がある場合、そのページ／ファイルを開いて読了してから書く。読まずに書き始めない。
* **差分中心に書く（DRY）**: 参照先が既に定義している内容は、原則「〜は[参照先]に従う」と委譲し、対象ドキュメント固有の差分（追加・変更・逸脱）を中心に書く。読者の理解に必要な範囲での部分引用は許可する。一方、一覧・表・定義をそのまま大量に書き写す丸写し（引用の多用）は不可。
* **重複の自己点検**: 各段落が参照先や他セクションの丸写しになっていないかを確認し、丸写しは参照への委譲と必要最小限の引用に置き換える。

## 1. 基本原則（3C）

技術文章においては、以下の3つの「C」を常に意識します。

* **Correct（正確）**: 事実関係やデータに誤りがない。
* **Clear（明確）**: 読み手が意味を迷う余地がない。
* **Concise（簡潔）**: 最短の言葉で情報を伝える。

## 2. 文章構造と構成

読み手が知りたい情報にすぐ辿り着けるよう、視覚的に構造化します。

### 2.1 パラグラフ・ライティング

* 1つの段落には、1つのトピックだけを書く。
* 段落の冒頭に、その段落で最も伝えたいこと（要旨）を記述する。

### 2.2 リストの活用

箇条書きは便利ですが、多用しすぎると「情報の関連性」や「論理の繋がり」が欠落します。以下のルールを適用してください。

- 「3つ以上」の並列要素がある場合のみ使用: 2つの要素であれば、句読点（A、およびB）で繋ぎ、一文で記述する。
- 文脈が必要な場合は地文で書く: 理由や背景など、前後の論理的な繋がりが重要な内容は、箇条書きにせず通常の文章（地文）で説明する。
- リストの階層は2段まで: 階層が深すぎると視認性が下がるため、3階層以上になる場合はセクション（見出し）を分ける。
- リストの直前に導入文を置く: 突然リストを始めず、「理由は以下の通りです。」「以下の手順で実行します。」といった導入文を必ず添える。

### 2.3 章立ては内容から決める

テンプレートの見出しを機械的に並べない。各見出しは、他の見出しに書かれていない判断を1つだけ受け持つ。

- 要旨・目的・ゴール・非ゴール・背景のように役割の近い枠を並べると、同じ主張を複数回書くことになる。提案そのものを要旨と本文の両方に書いていないか、目的を背景と要旨の両方に書いていないかを確認する。
- 残す基準は「そこにしか書かれていない情報があるか」。ゴールが提案の言い換えになっているなら削る。非ゴールは扱わない範囲の境界を定めるため、他に書き場所がないことが多い。
- 文書の用途に不要な枠を置かない。設計を決めるための文書に、担当者・期限・決裁者・承認状況は要らない。

### 2.4 ディテールは結論を支える分だけ書く

- 障害の連鎖や処理の流れを逐条で説明する前に、結論を1文で書く。読み手が結論を受け入れるなら、途中の段は読まれない。
- 手順の逐一列挙は、実行者が参照する文書に置く。方針を判断する文書では、作業のまとまりと規模が分かれば足りる。
- 試算は前提が確定しているものだけ数値で書く。未計測の値を使う試算は式だけを残す。
- 口頭で出た見込みや裏の取れていない数値を、事実として書かない。出典を示せないなら数値を落として定性的に書く。3.2 が求める具体化は、書き手が確かめた事実を曖昧にぼかさないという意味であり、確かめていない値を数値で書いてよいという意味ではない。

### 2.5 出典は本文から分離する

- `file:line` 形式の参照を本文に散らすと主張が読み取りにくくなる。本文は主張だけを書き、出典は付録の表か別資料にまとめる。
- 修正対象のファイルを指す記述は出典ではなく作業指示なので、本文に残す。
- 出典をリンク付きの別資料に持たせたなら、文書側の出典一覧は削る。同じものを2箇所で保守しない。

## 3. 執筆ルール（スタイルガイド）

### 3.1 文の長さと接続

* **一文一義**: 一つの文章に情報を詰め込まず、60文字程度を目安に句点（。）で区切る。文字数に数えるのは日本語の散文だけで、コード・識別子・URL・コマンドは数えない。60文字を超える場合は、分割すると意味や断定の強さが変わる理由を示す。
* **順接の明確化**: 「〜が、」は逆接と順接の両方で使われるため、順接の場合は「〜であり、」や「〜。そして、」に置き換える。

### 3.2 表現の具体化

* **指示代名詞の禁止**: 「これ」「それ」は指し示す対象が不明確になるため、固有名詞や名詞を再掲する。
* **曖昧表現の排除**: 以下の言葉は、数値や具体的な状態に置き換える。
* 不適切：*「しばらく待ってから」「適切に設定し」「適宜確認」*
* 適切：*「30秒待機し」「[有効]を選択し」「ログを1日1回確認」*

### 3.3 態と動詞

* **能動態の使用**: 「〜される」という受動態を避け、「〜する」という能動態で記述する。（例：「設定が保存される」→「システムが設定を保存する」）
* **冗長な補助動詞の削除**: 「〜を行うことが可能である」→「〜できる」または「〜する」。

## 4. 表記の統一（トーン＆マナー）

| 項目 | ルール | 例 |
| --- | --- | --- |
| **用語** | 同一の対象には同一の用語を使う | 「ユーザー」「ユーザ」を混在させない |
| **送り仮名** | 公用文または業界標準に合わせる | 「割り当て」「割当て」「割当」の統一 |
| **記号** | UI上の項目はブラケットで囲む | `[設定]` ボタン、`「ファイル」` メニュー |
| **数字** | 原則として半角算用数字を用いる | 10個、24時間、Version 2.0 |

## 5. 推敲チェックリスト

提出・公開前に以下の項目を確認してください。

* [ ] 主語と述語は正しく対応しているか？
* [ ] 専門用語に対して注釈や定義は不足していないか？
* [ ] 箇条書きのレベル（階層）は適切か？
* [ ] 冗長な「という」「のこと」などは削られているか？
* [ ] 参照先の内容を丸写ししていないか？（委譲と必要な部分引用に留めたか）
* [ ] 同じ主張を複数の見出しで書いていないか？
* [ ] 文書の用途に不要な枠（担当者・期限・承認）が混ざっていないか？
* [ ] 本文に `file:line` の出典が散らばっていないか？
* [ ] 裏の取れていない数値を事実として書いていないか？

---

## 6. 最終レビュー

執筆・推敲が完了したら、必ず `develop:docs-review` スキルを実行する。対象種別には「ファイル」を指定し、編集したファイルの絶対パスを渡す。本スキルのルール（3C・執筆ルール・推敲チェックリスト）がそのままレビュー基準となる。
