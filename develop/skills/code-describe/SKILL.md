## 1. 呼び出しタイミングと適用範囲

資料の目的は、読み手が自分でコードを追わなくても妥当性を判断できる状態にすることにある。

対象は、読み手がコードと突き合わせて確認する資料。入口は 2 つあり、出力先は入口ごとに決まる。

### 1.1 自分の実装を説明する

対象は手元にあるので 2 章は飛ばし、3 章から始める。出力先は lensdiff に渡す資料にする（6 章）。

`develop:ship` の lensdiff レビューでは、差分の種類と規模によらず `overview.md` と `explanations.json` を必ず作る。差分の規模に合わせて減らすのは節ではなく分量で、小さい差分では 6.1 の各節を数行にする。判断を含む hunk がなければ `explanations.json` は空配列 `[]` にして渡す。次のいずれかを含む差分では、図・代案・依存先の挙動まで書く。

- 複数のリポジトリにまたがる
- 差分の行を読むだけでは、変更前後の挙動の違いが分からない
- 既存の挙動に依存した判断を含み、その依存がコードを見ないと分からない

### 1.2 他人の PR を説明する

レビュー依頼や共有のために、既存の PR の仕組みをまとめる場合に使う。2 章の読み方から始める。出力先はアーティファクトにする。

## 2. 他人の PR を読む

この章は 1.2 の入口でのみ使う。

### 2.1 対象を手元に用意する

差分だけを読んで説明を書かない。呼び出し元・呼び出し先・型定義を追えないため、因果を取り違える。

同じセッションで clone 済みのリポジトリがあれば、再 clone せずそれを使う。無い場合だけ clone する。パスは作業ディレクトリからの形式で書く。

```sh
gh repo clone 組織/リポジトリ repos/対象ディレクトリ
mise trust repos/対象ディレクトリ
cd repos/対象ディレクトリ && gh pr checkout {番号}
```

`mise trust` は `mise.toml` があるリポジトリだけで必要になる。これを飛ばすと、リポジトリが固定したバージョンではなくグローバルの古いツールで動かすことになる。

### 2.2 リポジトリが固定したバージョンで検証する

差分に実行されるコードが含まれるときだけ行う。ドキュメントや設定だけの PR では飛ばす。

1. `.python-version` や `mise.toml` など、リポジトリが固定しているバージョンを読む
2. そのバージョンでテスト・型チェック・lint を流す
3. 結果を資料に書くときは、コマンドと件数を添える

グローバルに入っているツールで流して落ちても、それが PR の欠陥とは限らない。言語バージョンによって、同じコードが構文エラーにも正しいコードにもなる。実例として、Python 3.14 の PEP 758 は括弧なしの `except A, B:` を認めるので、3.13 以前で読むと構文エラーに見える。

CI の pass だけを根拠にしない。新規ディレクトリが CI の対象に入っていないことがある。

### 2.3 既出の指摘を確認する

`gh pr checks` が pass でも、bot のレビューは指摘を残したまま check を通す。未 resolve のスレッドを先に読み、既出の指摘を資料に書き直さないようにする。

取得の手順は `develop:pr-review-fix` の「コメントの resolve」にあるクエリに従う。

## 3. コードの説明の粒度

説明の粒度は、読み手が grep して照合できる水準に合わせる。抽象語でまとめた説明は確かめようがないので、資料としての役に立たない。

### 3.1 「何をするか」ではなく「なぜその書き方か」を書く

関数名を言い換えただけの説明は、差分を読めば分かるので書かない。書くのは、その実装を選んだ理由と、他の書き方を選ばなかった理由になる。

- step を 2 つに分けた理由（片方の再試行で、成功済みの側を二重に作らないため）
- 例外を投げずにデータで返す理由（投げると後続の後始末に到達しないため）
- 値を関数の外ではなく中で取る理由（外で取ると再実行時にずれるため）

### 3.2 抽象語ではなくコード中の実物を書く

曖昧表現の排除そのものは `develop:docs-write` の「表現の具体化」に従う。コードの説明では、次をそのまま本文に置く。

- **定数**: 名前と値を併記する（`POLL_MAX_ATTEMPTS`（290））
- **設定**: 環境変数名で書く
- **エラーコード・状態**: コード中のリテラルをそのまま書く
- **各段の戻り値の型**: `prepare → list[PreparedFile]` のように書く。型が分かると、段と段の間で何が保たれるかが読み取れる
- **分岐**: 判定式そのものを書く（`shared_running >= 閾値`）。読み手が境界値を検討できる

### 3.3 書かないもの

- 追加した節名・ファイル名の列挙
- コードブロックの丸写し。必要なのは引用ではなくリンク
- 未検証の推測。事実の扱いは `develop:docs-write` の「ディテールは結論を支える分だけ書く」に従う

## 4. リンクの作り方

この章のリンクは、アーティファクトのために作る。lensdiff に渡す資料では解説が行そのものに付くので、リンクは要らない（6.2）。

### 4.1 クリックできるリンクにする

`file:line` をそのまま書かない。GitHub のリンクにする。読み手が開いて確かめられること自体が、この資料の価値になる。形式は次の通り。

```
https://github.com/{owner}/{repo}/blob/{sha}/{path}#L{開始行}-L{終了行}
```

### 4.2 コミットの SHA に固定する

ブランチ名を指すリンクは、後のコミットで行がずれて別の箇所を指す。`main` や `HEAD` を使わない。

SHA は `git -C {リポジトリ} rev-parse HEAD` で取る。資料の末尾に、固定したコミットを明記する。読み手が「いつ時点のコードか」を判断できるようにするため。

レビュー指摘を直して push したら、SHA と行番号を取り直して資料を貼り直す。固定したまま放置すると、リンクは開けるが修正前のコードを指す。

### 4.3 リポジトリ名を添える

複数のリポジトリにまたがる資料では、パスだけではどのリポジトリか判別できない。各リンクにリポジトリ名を併記する。

## 5. 資料の組み立て

### 5.1 全体像の図を先に置く

処理の流れを扱う資料では、構成図を先に示してから各段の詳細に入る。読み手が現在地を見失わないようにするため。

図は次を満たす。

- **矢印にラベルを付ける**: ラベルのない矢印は「何か関係がある」としか言えない。何が流れるかを書く
- **境界を描く**: 別のクラウド・別のアカウント・別のリポジトリをまたぐ箇所は、ゾーンで囲って色を変える。どこで信頼境界を越えるかが、たいてい説明の中心になる
- **クラウドのサービスは公式アイコンで描く**: AWS なら AWS Architecture Icons を使い、サービスを汎用の箱で代用しない。読み手はアイコンでサービスを見分けるため。境界（AWS Cloud・アカウント・リージョン）も公式の枠線色と group アイコンで描く

アーティファクトは外部画像を読み込めないので、アイコンの SVG（例: npm の `aws-icons`）を取得して data URI で埋め込む。

インライン SVG の書き方は、`artifact-diagramming` が使える環境ではそれに従う。

### 5.2 出典は主張と同じ行に置く

出典を末尾にまとめると、読み手が主張と行き来することになる。処理の流れを説明する資料では、各ステップに「誰が誰に何を」と出典をセットで置く。

本文から出典を分離するかどうかの判断は `develop:docs-write` の「出典は本文から分離する」にある。本スキルは、分離したあとの資料をどう作るかを扱う。

### 5.3 設計の肝を独立させる

実装全体がひとつの制約から導かれている場合、その制約を独立した節にする。各段の説明に溶かし込むと、読み手が制約を再構成することになる。

## 6. lensdiff に渡す資料を作る

1.1 の入口では、`overview.md` と `explanations.json` をスクラッチパッドに作り、lensdiff の `--overview` と `--comment` で渡す。オプションと JSON の形式（解説は `kind: "explanation"`）、Overview タブで表示できるものは `lensdiff` スキルに従う。本章は何をどれだけ書くかを扱う。

### 6.1 overview.md に置くもの

次の節をこの順に置く。条件付きの節は、条件に当てはまる差分でだけ置く。

- **全体像**: 5.1 の構成図を Mermaid で、差分が持つ観点ごとに 1 枚ずつ描く。1 枚に詰めると、データの形と処理の順序が混ざって読み取れないため。矢印のラベルと境界の条件は 5.1 に従い、境界は `subgraph` で囲む
  - 差分が処理の経路を変えるとき: リクエストから永続化・外部呼び出しまでを `flowchart` で描く
  - 差分がテーブル・カラムを追加・変更するとき: テーブル間の関係を `erDiagram` で描く。列の網羅は次のテーブル定義に書く
  - 差分が実行環境・デプロイ経路を変えるとき: その経路を `flowchart` で描く
  - 差分が複数段の呼び出し・ロック・トランザクションを含むとき: 順序を `sequenceDiagram` で描く
- **テーブル定義**（差分がテーブルを新規作成・変更するとき）: テーブルごとに列を Markdown の表にし、その下にインデックス・ユニーク制約・トリガー・GRANT を箇条書きで並べる。制約の漏れや既定値の誤りを、マイグレーションを開かずに照合できるようにするため。`erDiagram` は型と PK/FK までしか持てず、既定値・CHECK・インデックスを表せない
  - 新規作成したテーブル: 列を省略せず、DDL どおりに全列の型・NULL 可否・既定値・PK/FK と ON DELETE・CHECK を書き、インデックス・ユニーク制約・トリガー・GRANT もすべて書く
  - 既存テーブルへの変更: 追加・変更した列と、追加・変更した制約・インデックスをすべて書く
- **設計の肝**: 5.3 の制約と主要な判断を 1 項目ずつ置き、各項目に選んだ理由と選ばなかった代案を添える（3.1）
- **API 表**（差分がエンドポイントを追加・変更するとき）: エンドポイントごとに、必要な最小ロール・成功時のステータス・エラー時のステータスとエラーメッセージのリテラルを 1 行にする。権限とエラーの網羅を、実装を開かずに照合できるようにするため
- **並行性**（差分がロック・トランザクションを含むとき）: ロックごとに、取る操作・取得順・デッドロックしない理由を書く。競合はテストで再現しにくく、レビューで確かめるしかないため
- **対象外の参照元への影響**（差分が共有されているものを変えるとき）: grep で数えた参照元の件数と、挙動が変わらない根拠（または合意済みの変化）を書く。テストの pass は影響がない根拠にならないため
- **既知の制約・許容した残課題**: 意図して残したものと、許容した理由を書く。書かないと、レビューで見落としとして指摘され、同じ議論を繰り返すため
- **読む順番**: 読み始める箇所を `path/to/file.ts:123` 形式のインラインコードで並べる

### 6.2 explanations.json に置くもの

判断を含む hunk ごとに 1 件作り、3 章の「なぜその書き方か」を、その判断を書いた行範囲に置く。解説が行の上に表示されるため、5.2 の「出典は主張と同じ行に置く」がそのまま満たされる。

判断を含む hunk を拾い漏らさないよう、差分をファイルごとに先頭から通読し、各 hunk を次のチェックリストと照らす。リストは判断が入りやすい箇所の例で、網羅ではない。数件を抜き出すだけでは、解説のない hunk の判断を読み手が自分で再構成することになるため。

- **スキーマ・マイグレーション**: テーブルの用途、外部キーごとの `ON DELETE` の選択、インデックスごとにそれが支えるクエリ
- **クエリ・データ取得**: 絞り込み条件、ロックモード、並び順、ページング
- **認可・エラー時の応答**: 返す結果（404 と 403 のどちらを返すか など）とその理由
- **トランザクション・状態更新の境界**: どこまでを一括で確定させるか
- **入力の定義**: バリデーションの上限値と必須項目、それぞれの理由
- **実行環境・設定**: 値の経路と、その値にした理由
- **削除・後始末**: 消す順序と、消し残しが出ない理由
- **サイズ・上限の判定**: 判定式と境界値の根拠
- **権限・GRANT**: 付与する権限と、それより広く付けない理由
- **テスト**: 各テストが固定する挙動と、その DB・環境（Postgres か SQLite か など）を選んだ理由

判断を含まない hunk（リネーム・import・生成コード）には付けない。密度の参考として、約 1600 行のバックエンドの差分では 76 件程度になる。

各件の本文は 3 章に従う。

行番号は、本文が述べる行を HEAD のファイルで読みながら取り、そのコードがその行にあることを確かめる。ずれた解説は、別のコードの理由として読まれるため。

## 7. 公開前に確認する

- **共有範囲**: アーティファクトは作成時の共有範囲が一定ではない。リンクを渡すときに、相手が開けるかどうかを伝える。開けない場合は共有操作が必要なことも添える
- **リンクの指し先**: SHA・パス・行番号のいずれかを取り違えると、リンクは開けるが別の箇所を指す。行番号は資料を書いた時点のものか確認する
