# ship: 依頼から PR マージ待ちまで

ユーザーに聞くのは末尾の「止めて聞く場面」だけにし、それ以外は既定で決めて進め、決めたことを最後に報告する。作業先の `AGENTS.md`・`CLAUDE.md` が足す手順は該当する段に入れ、食い違えば作業先に従う。手順は差分の規模で省かない。省いてよいのは作業先が定めるときだけ。門番 hook に手順の抜けで止められたら、止められた段の手順を頭から回す（hook を通すことを目的にしない）。

## 責任の分担

メインエージェントは manager、サブエージェントは developer として、責任を次のように分ける。developer の作法は agent 定義（`develop:developer`）が持つ。

| | manager（メインエージェント） | developer（サブエージェント） |
| --- | --- | --- |
| 決める | 何を達成するか（目的・要件・範囲・完了条件）と、受け入れるか | どう作るか |
| 責任を持つ | 要件がユーザーの意図と合っていること。受け入れた成果物 | 成果物が作業先の規約に合っていること。その根拠を返すこと |
| 確かめる | developer の視野の外（依頼の意図・タスク間の整合・差分の外への影響）。規約との照合は、受け入れの責任として developer の報告や依頼文に頼らず独立に行う | 自分の差分が規約とテストを満たすか |

- 気になる点は、答えではなく、developer が規約で判断する問いとして依頼文に書く。
- 受け取ったら、developer の報告に根拠が揃っているかを見る。足りなければ自分で補わずに差し戻す。
- 段ごとの受け入れの観点ごとに、見つけたこと（なければ何を確かめたか）を台帳に残す。developer が回したテストやゲートは回し直さない。

## 1. 準備

- デフォルトブランチにいたら fetch してブランチを作る。base は `origin/HEAD` のブランチ（Stack PR の上側は下側のブランチ）。
- 依頼の解釈が割れるとき、または 3 タスク以上になるときは、実装の前に設計する。タスクは、触るファイル（とそのテスト）ごとに 1 件と数える。依頼文に手順が書いてあっても、判断を委ねられた点（「必要なら」「判断してよい」など）が 1 つでもあれば設計する。実装に入る前に、判定を scratchpad の台帳の先頭に `設計: 要｜不要（タスク N 件。決めた点: …。聞く点: …）` と書く。設計書は Claude Docs のアーティファクト（`Artifact` の quickstart → Docs 型）に書き、作る範囲の最小（何を作り、何を作らないか）を置く。会話を知らないサブエージェントに読ませて「推測が要り、外すと作るものが変わる点」を挙げさせ、各点を次のように扱う。委ねられた点と、依頼・規約・一次情報から決まる点は、自分で決めて根拠を設計書に書く。どちらでもない点は「止めて聞く場面」に当たるので、その点だけを 1 回で聞き、設計書全体の承認は求めない。聞く点がなければ、そのまま実装に入る。実装は設計書の範囲で止める。作るものが広がったら（文面の修正のはずがスクリプトを作る、など）、実装を止めて設計書に戻り、広げる理由を書いてから続ける。タスクごとの計画（範囲と、タスク間で受け渡す名前と形）は scratchpad に置く。

## 2. 実装

差分の種類は `bash <skill-dir>/classify-diff.sh <repo-dir> <base> [session_id]` で判定する（`<skill-dir>` はこのスキルのベースディレクトリ）。実装前は依頼から見込む。

- `docs`（変更が `*.md` か `docs/` 配下だけ）: メインエージェントが編集する。
- `code`: `develop:developer` に任せる。
- `shared`（共通関数・public API・既定値を変える）: `develop:developer` に任せる。実装前に参照元を grep で全数挙げ、依頼の対象外の挙動は opt-in で保つ。対象外の挙動が変わるなら一覧を示して合意を取る。

タスクごとに、`develop:developer` に実装させる → 別のサブエージェントでレビュー → Critical・Important を修正、を回す。3 回で収まらなければ能力の高いモデルに引き継ぐ。最後に最も能力の高いモデルでブランチ全体をレビューし、まとめて直す。進み具合と、どの developer が何を作ったかは scratchpad の台帳に残す。

developer の成果物の受け入れの観点:

- **規約との照合**: 差分のファイルごとに従う規約ファイルを、作業先の `AGENTS.md` から辿って対にした表を台帳に作る（文書の差分なら文書の規約、コードならコードの規約）。表の規約ファイルをすべて開き、規約の箇所と差分の箇所の対を残す。依頼文どおりであることは、規約に合う根拠にならない。
- **依頼の意図**: ユーザーとのやり取りで出たのに、渡した要件に入っていない条件が満たされているか。
- **設計書の範囲**: 設計書を書いたとき、差分が「作らないもの」に踏み込んでいないか。CI と bot の指摘への対応（5. PR の手順 6）でも同じく見る。
- **タスク間の整合**: ほかのタスクや既存のコードと、名前・データの形が揃い、処理が重複していないか。
- **直し方の深さ**: 症状への継ぎ当てになっていないか。同じ原因が差分の外に残っていないか。
- **差分の外への影響**: 設定・インフラ・他リポジトリ・データ・ドキュメントのうち、変えるべきなのに変わっていないものがないか。
- **独立した検証**: developer が回していない種類の検証を 1 つ回す。

自分で書いた文書と lensdiff の資料の受け入れの観点（会話を知らない読み手の立場で見る）:

- **規約との照合**: developer の成果物と同じく、文書の規約を開いて照らす。
- **前提の抜け**: 会話の中でだけ決まったことが抜けていないか。
- **読み手の疑問**: なぜこの方法か、ほかの案は、影響範囲は、に答えているか。
- **古い記述**: 変えた事実が、別の文書に古いまま残っていないか。

## 3. simplify と AI レビュー

`simplify` スキルで差分全体を 4 観点で見直し、意図した挙動を保つ指摘を採用する。続けて観点ごとにサブエージェントで AI レビューし、指摘を、該当行と問題が起きる入力や手順を添えて `kind: "finding"` の JSON で scratchpad に書かせる（`code` は correctness ほか、`docs` は整合性、`shared` は対象外の参照元を含める。2 の全体レビューを correctness とする）。`error` は直して commit し、`info`・`warn` は 4 で lensdiff に流す。simplify で採用しなかった指摘も、メインエージェントが `warn` の finding として findings JSON に書き起こし、4 で lensdiff に流して人が決める。

指摘の受け入れの観点:

- **覆えていない観点**: レビューの観点から漏れた領域がないか。あれば足してもう一度回す。
- **共通の根**: 複数の指摘が同じ原因から出ていないか。出ていれば原因を直す。
- **採否**: `error` は採否と理由を、5 の手順7の最終報告に並べる。

## 4. lensdiff レビュー

人の承認を得る段。ツールの使い方は `lensdiff` スキルに従う。未導入ならサンドボックスを外して入れる。

```sh
command -v lensdiff >/dev/null || npm install -g https://github.com/komtaki/lensdiff/releases/latest/download/lensdiff.tgz
[ -e ~/.claude/skills/lensdiff ] || npx skills add komtaki/lensdiff --skill lensdiff -g -a claude-code -y
```

1. `develop:code-describe` で `overview.md` と `explanations.json` を作る。`shared` の `overview.md` には「対象外の参照元への影響」の節（参照元の数と、挙動が変わらない根拠または合意済みの変化）を置く。
2. `<repo-dir>` で `lensdiff --merge-base HEAD origin/<base> --overview <overview.md> --comment "$(cat <explanations.json>)" --comment "$(cat <findings.json>)"` を、サンドボックスを外してバックグラウンドのシェルで起動する。`<findings.json>` は「3. simplify と AI レビュー」の `info`・`warn` の指摘。
3. 最終行が `✅ Approved`、またはタブを閉じてコメントが出なかったときは承認（閉じることが承認の意思表示なので聞き直さない）。指摘付きの承認なら直して commit する。承認なしの指摘は、直して commit し、解説と指摘の行番号を取り直し、修正で増えた hunk の解説を足して 2 からやり直す。
4. 承認したら `bash <skill-dir>/approve.sh <repo-top> <base>` で承認を記録する（プロジェクトの門番 hook が読む）。以降の修正は commit して 5 へ進む。

## 5. PR

1. push し、`develop:pr-writer` にブランチ・base と、今の差分について差分から読めない事実（未マージの依存、既定で決めたこと、確かめた根拠とその結果、apply やデプロイの順序、許容した残課題）を渡して、draft PR を作らせる。本文は base との差分の最終形を説明するものなので、材料も最終形についての事実にそろえる。
2. `gh pr view` で本文を検品し、直す点は同じ pr-writer に `SendMessage` で伝える。少量でも自分では直さない。書き手と検品者が分かれないと検品にならないため（`check-pr-command.sh` が止める）。
3. CI は `ccd_pr` があれば bind して auto-fix に任せる。なければ `gh pr checks <番号> --watch --fail-fast` をバックグラウンドで待ち、失敗したら `develop:developer` に直させる。
4. CI完了後 bot は指摘を残したまま check を通すので、`develop:pr-review-fix` で未 resolve スレッドに対応する（push 直後に空なら約 5 分後に 1 回取り直す）。
5. 差分が変わったら、`gh pr view --json body` から、今の差分にも当てはまる差分で読めない事実だけを拾い、手順1の材料と同じ形にして PR 番号と一緒に pr-writer に渡し、書き直させる。
6. CI の修正（auto-fix を含む）と bot の指摘への対応は、次の観点で受け入れる。
   - **同じ種類の問題**: 指摘された箇所以外にも、同じ種類の問題がないか。
   - **目的との食い違い**: 修正が、PR の目的や lensdiff で承認された内容を変えていないか。変えていれば、本文を書き直させる。
7. 既定で決めたことと、台帳の「決めた点」を、最終報告に並べる。

## 止めて聞く場面

| 場面 | 理由 |
| --- | --- |
| 本番リソースの削除など、取り消せない操作 | 戻せない |
| 外すと作るものが変わる点が、委ねられておらず、依頼・規約・一次情報のどれからも決まらない（その点だけを聞く） | 作り直しになる |
| `shared` で対象外の挙動が変わる | 他の利用者に影響する |
| 人間のレビュアーへの返信 | 返信案を見せ、本人が返す |
| lensdiff の承認 | 人の判断そのもの |
